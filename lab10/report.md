# Отчёт по лабораторной работе №10
## Тема: Построение CI/CD конвейера (GitLab CI, Docker, Kubernetes)


---

###  Краткое резюме
В ходе работы был развернут полноценный конвейер доставки приложения. Реализован многоэтапный пайплайн: статический анализ (flake8), модульное тестирование (pytest), сборка Docker-образа, сканирование уязвимостей (Trivy) и автоматический деплой в кластер K3s. Для управления конфигурацией использована подстановка переменных через `envsubst`, а для безопасности внедрен механизм ручного отката (`rollout undo`).

---

###  Ответы на контрольные вопросы

1. Shell executor vs Docker executor
Shell executor запускает команды прямо в ОС хоста. Из-за этого все зависимости (python, docker, kubectl) приходится ставить заранее, а система постепенно «загрязняется». Мы выбрали Docker executor, потому что он даёт изоляцию: каждый job выполняется в чистом временном контейнере с нужным образом (например, python:3.11 для тестов, trivy для сканирования). Так достигается воспроизводимость и безопасность.

2. Artifacts vs Cache

Artifacts — это ценные результаты работы job'а. GitLab их сохраняет и передаёт в следующие stages или даёт скачать (например, report.xml для отображения отчёта о тестах в UI).

Cache — временное хранилище для ускорения повторяющихся операций (например, .cache/pip для загрузки пакетов). Кэш может быть очищен в любой момент, и его сохранность не гарантируется.

3. Роль директивы needs
По умолчанию stages идут строго последовательно: все job'ы стадии должны завершиться, прежде чем начнётся следующая. Директива needs: [lint-python] строит направленный ациклический граф (DAG). Job build-image стартует сразу после успешного завершения lint-python, не дожидаясь остальных параллельных job'ов стадии lint. Это заметно сокращает общее время пайплайна.

4. Безопасность: Masked Variable и File
CI_REGISTRY_PASSWORD помечается как Masked, чтобы его значение заменялось на [MASKED] в логах и пароль не утёк. KUBE_CONFIG передаётся как File (или декодируется из base64 в файл), потому что держать длинную строку с сертификатами и токенами в обычной переменной опасно: она может случайно попасть в логи при выводе ошибок kubectl, а форматирование может сломаться из-за спецсимволов. Файл же позволяет выставить строгие права chmod 600.

5. Зачем нужен docker:24.0.5-dind
Job'ы выполняются внутри изолированного контейнера, у которого нет собственного Docker-демона. Сервис dind (Docker-in-Docker) поднимает второй контейнер с демоном, к которому основной контейнер job'а подключается по сети (через DOCKER_HOST). Это даёт возможность выполнять docker build и docker push внутри CI, не монтируя опасный сокет хоста (/var/run/docker.sock).

6. Роль envsubst и отказ от тега latest
envsubst подставляет значения переменных окружения GitLab (например, $APP_VERSION) в шаблон YAML перед отправкой в kubectl. Тег latest мы не используем, потому что он нарушает идемпотентность: если образ обновился, а тег остался latest, Kubernetes не увидит изменений в манифесте и не перезапустит поды. Тег с коротким хешем коммита ($CI_COMMIT_SHORT_SHA) гарантирует точную привязку версии кода к запущенному контейнеру.

7. Как работает kubectl rollout undo
Kubernetes хранит историю изменений Deployment в виде объектов ReplicaSet (по умолчанию последние 10). Команда rollout undo не пересобирает образ и не ищет старые файлы — она просто переключает указатель Deployment на шаблон пода предыдущего ReplicaSet. Кластер «помнит» предыдущую версию благодаря аннотации deployment.kubernetes.io/revision на объектах ReplicaSet.

8. Лимиты ресурсов и OOMKilled
limits.memory: "128Mi" защищает узел кластера от деградации: один под не сможет монополизировать память. Если приложение попытается выделить больше, ядро Linux задействует OOM Killer для cgroup этого контейнера. Процесс будет принудительно завершён с кодом 137 (SIGKILL). В выводе kubectl get pods это отразится статусом OOMKilled в поле LAST STATE, а счётчик RESTARTS увеличится, так как kubelet попробует перезапустить контейнер.
