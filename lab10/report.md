# Отчёт по лабораторной работе №10
## Тема: Построение CI/CD конвейера (GitLab CI, Docker, Kubernetes)

1. Чем Shell-исполнитель отличается от Docker-исполнителя и почему выбран Docker?
Shell-исполнитель запускает команды прямо в ОС хоста: все зависимости (python, docker, kubectl) приходится ставить заранее, а система постепенно «загрязняется». Docker-исполнитель изолирует каждое задание в чистом временном контейнере с нужным образом (python:3.11 для тестов, trivy для сканирования). Это даёт воспроизводимость и безопасность, поэтому использовали именно его.

2. Чем артефакты отличаются от кэша?
Артефакты — ценные результаты задания, которые GitLab сохраняет и передаёт дальше по этапам или отдаёт на скачивание (например, report.xml для отображения отчёта о тестах в интерфейсе).
Кэш — временное хранилище для ускорения повторяющихся операций (например, .cache/pip для пакетов). Кэш могут очистить в любой момент, его сохранность не гарантируется.

3. Что даёт директива needs?
По умолчанию этапы идут строго последовательно: следующий стартует только после завершения всех заданий предыдущего. Директива needs: [lint-python] строит направленный ациклический граф (DAG): задание build-image стартует сразу после успеха lint-python, не дожидаясь остальных параллельных заданий этапа lint. За счёт этого общее время пайплайна заметно сокращается.

4. Зачем нужны маскированная переменная и передача KUBE_CONFIG файлом?
CI_REGISTRY_PASSWORD маскируется, чтобы в логах вместо значения выводилось [MASKED] — это защищает от утечки пароля. KUBE_CONFIG передаётся как File (или декодируется из base64 в файл), потому что длинную строку с сертификатами и токенами опасно держать в обычной переменной: она может случайно попасть в логи при ошибках kubectl, а спецсимволы способны нарушить форматирование. Файл же позволяет выставить строгие права chmod 600.

5. Для чего нужен сервис docker:24.0.5-dind?
Задание выполняется в изолированном контейнере, где своего Docker-демона нет. Сервис dind (Docker-in-Docker) поднимает второй контейнер с демоном, к которому контейнер задания подключается по сети через DOCKER_HOST. Так можно выполнять docker build и docker push внутри CI, не монтируя опасный сокет хоста (/var/run/docker.sock).

7. Как работает kubectl rollout undo?
Kubernetes хранит историю изменений Deployment в виде объектов ReplicaSet (по умолчанию — последние 10). Команда rollout undo не пересобирает образ и не ищет старые файлы: она просто переключает указатель Deployment на шаблон пода предыдущего ReplicaSet. Кластер знает предыдущую версию благодаря аннотации deployment.kubernetes.io/revision на объектах ReplicaSet.

8. Зачем нужны лимиты ресурсов и что такое OOMKilled?
limits.memory: "128Mi" защищает узел от деградации, не давая одному поду забрать всю память. Если приложение запросит больше, ядро Linux включит OOM Killer для cgroup этого контейнера, и процесс будет принудительно завершён с кодом 137 (SIGKILL). В kubectl get pods это видно как статус OOMKilled в поле LAST STATE, а счётчик RESTARTS растёт, поскольку kubelet пытается перезапустить контейнер.
