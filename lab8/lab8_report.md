Отчет по лабораторной работе №8
Тема: Пакетирование приложений и организация мониторинга в Kubernetes с помощью Helm

В ходе лабораторной работы были освоены принципы управления приложениями в Kubernetes через пакетный менеджер Helm. Реализован полный жизненный цикл чарта: от создания шаблонов и настройки параметров до обновления и аварийного отката. Продемонстрирован подход к разделению конфигураций для различных сред (dev/prod). Кроме того, с нуля разработан и развернут легковесный стек мониторинга (Prometheus + Grafana), настроен сбор метрик и создана визуальная панель управления состоянием кластера.

 Ход выполнения и результаты

Часть A: Основы Helm и управление релизами
Был инициализирован базовый чарт myapp-chart. Из стандартной структуры удалены избыточные компоненты (HPA, Ingress, тесты) для фокусировки на базовой функциональности. В файле values.yaml определены ключевые параметры: количество реплик, используемый образ (nginx:1.25-alpine) и строгие лимиты потребления ресурсов. Шаблоны Deployment и ConfigMap адаптированы для динамической генерации манифестов через механизм Go-templating.
Результат: Успешно протестирован сценарий обновления приложения (изменение заголовка через --set) и последующего аварийного отката (rollback) после имитации сбоя (указание несуществующего тега образа). История изменений корректно сохраняется.

Часть B: Управление окружениями и артефактами
Для демонстрации гибкости Helm созданы изолированные файлы переопределения: dev-values.yaml (минимальные ресурсы, 1 реплика) и prod-values.yaml (повышенные лимиты, 3 реплики). Релизы развернуты в разных неймспейсах (default и production), что подтверждает изоляцию сред.
Результат: Чарт успешно упакован в единый архив myapp-chart-1.0.0.tgz. Продемонстрирована установка приложения напрямую из этого бинарного артефакта, что имитирует процесс доставки кода из CI/CD-пайплайна.

Часть C: Разработка кастомного чарта мониторинга
Вместо использования тяжеловесного kube-prometheus-stack, который требует значительных ресурсов, разработан минималистичный чарт monitoring-chart. Он включает в себя:
Prometheus: с базовой конфигурацией scrape_configs для сбора метрик с узлов кластера.
Grafana: с предустановленной переменной окружения для задания пароля администратора и типом сервиса NodePort для внешнего доступа.
Результат: Оба компонента успешно запущены в выделенном неймспейсе monitoring в рамках заданных лимитов памяти (256Mi).

Часть D: Визуализация данных
Выполнена интеграция Grafana с Prometheus. В качестве источника данных (Data Source) указан внутренний адрес http://prometheus:9090, использующий встроенную DNS-систему Kubernetes. Создан дашборд "K8s Overview", содержащий индикатор состояния целей (метрика up) и панель для анализа активности в неймспейсах.


 Ответы на контрольные вопросы

1. Механика Helm Rollback: что происходит в кластере и где хранится история?
При выполнении отката Helm не применяет "магические" исправления, а действует детерминировано. Вся история релизов хранится в самом Kubernetes в виде зашифрованных объектов Secret в том же неймспейсе, где установлен чарт (имена имеют вид sh.helm.release.v1.<имя>.v<ревизия>). Команда rollback извлекает YAML-манифесты указанной прошлой ревизии из этого Secret и отправляет их в Kubernetes API. Кластер воспринимает это как изменение желаемого состояния и инициирует стандартный процесс Rolling Update, плавно заменяя текущие поды на версию из прошлого релиза. При этом в истории создается новая запись (например, откат к ревизии 1 создаст ревизию 4, идентичную первой).

2. Разбор конструкции Go Templating: {{- toYaml .Values.prometheus.resources | nindent 10 }}
Эта строка обеспечивает безопасную и корректную вставку блока ресурсов:
toYaml преобразует словарь (map) из файла values.yaml в валидную текстовую YAML-строку.
nindent 10 добавляет символ переноса строки и ровно 10 пробелов перед каждой строкой результата, чтобы соблюсти правильную вложенность в структуре YAML (уровень внутри containers).
Символ - сразу после {{ указывает шаблонизатору удалить все предшествующие пробелы и переносы строк в самом файле шаблона, предотвращая появление пустых, "мусорных" строк в итоговом манифесте.
Почему нельзя вручную? Жесткое прописывание нарушает принцип DRY (Don't Repeat Yourself). Если мы захотим изменить лимиты для prod-окружения, нам придется править сам шаблон, а не просто передать другой values.yaml.

3. Роль Kubernetes DNS при подключении Grafana к Prometheus
IP-адреса подов в Kubernetes эфемерны: при любом перезапуске или сбое под получает новый случайный IP. Жесткая привязка к IP сделала бы конфигурацию нерабочей после первого же инцидента. Мы используем имя prometheus, потому что встроенный DNS-сервер (CoreDNS) автоматически регистрирует запись вида prometheus.monitoring.svc.cluster.local. Когда Grafana отправляет запрос, CoreDNS резолвит это имя в стабильный виртуальный IP (ClusterIP) сервиса prometheus. Даже если под с базой данных метрик будет пересоздан и получит новый IP, Service останется прежним, а компонент kube-proxy прозрачно перенаправит трафик на актуальный под.

4. Resource Limits: последствия превышения и диагностика
Лимиты необходимы для изоляции сбоев и предотвращения ситуации "шумного соседа", когда одно приложение монополизирует ресурсы узла. Если контейнер попытается выделить 300Mi при лимите в 256Mi, ядро Linux активирует механизм OOM Killer (Out Of Memory Killer). Контейнер будет принудительно завершен с кодом ошибки 137 (SIGKILL), а в статусе пода появится пометка OOMKilled. После этого kubelet попытается перезапустить контейнер.
Команда для диагностики: kubectl describe pod <имя-пода> -n monitoring (в разделе Events будет явно указана причина OOMKilled).

5. Интерпретация PromQL запроса up
Метрика up является бинарным индикатором здоровья цели (target): значение 1 означает, что Prometheus успешно опросил эндпоинт за последний интервал, а 0 свидетельствует о неудаче (таймаут, отказ в соединении, ошибка 5xx).
Алгоритм поиска причины при значении 0:
Проверить физическое состояние подов: kubectl get pods -n monitoring.
Изучить события и логи проблемного пода: kubectl describe pod ... и kubectl logs ....
Убедиться, что Service корректно связывает имя с IP-адресами подов: kubectl get endpoints <имя-сервиса>.

6. Сравнение подходов: --set против -f values.yaml
--set предназначен для точечного, "хирургического" переопределения 1-2 параметров "на лету" (например, при быстром ручном тесте или передаче динамического тега Docker-образа из CI/CD-пайплайна). Его главный недостаток — катастрофическая потеря читаемости при попытке задать сложную конфигурацию.
-f values.yaml — это декларативный подход. Он предпочтителен для описания полных конфигураций окружений (dev/stage/prod). Файл можно версионировать в Git, подвергать код-ревью и гарантировать идемпотентность (повторяемость) развертывания в любой момент времени.

7. Смысл пакетирования (helm package) и сценарии использования .tgz
Команда helm package компилирует директорию с исходными шаблонами чарта в единый сжатый архив .tgz. Это превращает конфигурацию из набора файлов в полноценный, версионированный артефакт сборки.
Сценарии использования архива вместо папки:
Публикация в репозиториях: Загрузка чарта в приватные или публичные Helm-репозитории (ChartMuseum, Nexus, OCI-registry) для централизованного распространения.
Изолированные сети (Air-gapped): Передача чарта в защищенные контуры, где у кластера физически нет доступа к интернету или корпоративному Git.
Гарантия воспроизводимости: Фиксация конкретной версии для аудита и деплоя в production, что исключает риск случайного или злонамеренного изменения исходных файлов шаблонов между моментом тестирования и моментом релиза.
