## Часть A. Модуль и переиспользуемость

### Код модуля `modules/lxd_instance/main.tf`

Модуль принимает параметры: `name`, `cpu`, `memory`, `disk_size`. Создаёт ресурс `lxd_instance` с заданными параметрами.

### Вызов модуля в `environments/dev/main.tf`

Модуль вызван дважды:
- **web_server**: 2 CPU, 2GiB RAM, 15GiB диск
- **db_server**: 4 CPU, 4GiB RAM, 30GiB диск

## Часть B. Управление состоянием

Использованные команды:
- `terraform init` — инициализация
- `terraform plan` — план изменений
- `terraform apply` — применение
- `terraform state list` — список ресурсов
- `terraform state show` — детали ресурса

## Часть C. Настройка через Ansible

Плейбук `configure.yml` выполняет:
1. Установка Nginx
2. Развёртывание index.html
3. Запуск сервиса Nginx

## Часть D. Единый конвейер

Скрипт `deploy.sh` автоматизирует:
1. `terraform init` + `terraform apply`
2. Ожидание готовности SSH
3. Запуск `ansible-playbook`

## Вопросы и ответы

1. Разница между локальным модулем и провайдером

Это сущности разного уровня. Провайдер — это «драйвер» Terraform, плагин, который реализует взаимодействие с конкретным внешним API: LXD, AWS, Azure и т. п. Он определяет, какие типы ресурсов вообще существуют и как с ними работать через сетевые вызовы. Модуль же — это пользовательская надстройка: набор ресурсов (модулей, переменных, выходов), оформленный как переиспользуемый блок. Модуль не умеет общаться с API сам по себе — он опирается на провайдеры. Грубо говоря, провайдер отвечает на вопрос «чем управлять и как», а модуль — «какую логическую группировку ресурсов переиспользовать».

2. Зачем при переименовании модуля нужен terraform state mv

Terraform сопоставляет ресурсы в коде с записями в state по адресу (имени). Если модуль переименован, для Terraform это выглядит как «старый адрес исчез, появился новый»: старую запись он планирует удалить, новую — создать. В результате инфраструктура была бы разрушена и поднята заново. Команда state mv переписывает адрес в state без обращения к реальной инфраструктуре, поэтому ресурсы остаются на месте, а Terraform начинает «узнавать» их под новым именем.

3. Чем terraform apply -replace лучше ручного удаления

-replace выполняет пересоздание согласованно и атомарно с точки зрения state: Terraform сам удаляет старый объект и создаёт новый по текущему коду, одновременно корректируя state. При ручном удалении (например, через lxc delete) Terraform об этом не знает — в state остаётся запись об уже несуществующем ресурсе, возникает рассинхронизация, и последующий apply может вести себя непредсказуемо. Кроме того, -replace фиксирует намерение в плане, что делает операцию воспроизводимой и проверяемой до применения.

4. Как SSH-ключ попадает в контейнер

Цепочка такая: Terraform создаёт пару ключей ресурсом tls_private_key; открытая часть передаётся в модуль (как переменная/аргумент); при создании контейнера эти данные попадают в cloud-init, который на этапе первой загрузки записывает открытый ключ в /home/ubuntu/.ssh/authorized_keys. В результате пользователь ubuntu может подключаться по SSH с соответствующей закрытой частью, которая остаётся у Terraform (в state) и у владельца конфигурации.

5. Опасность хранения приватного ключа в state

State — это не только «карта» ресурсов, но и хранилище значений атрибутов, среди которых приватный ключ лежит в открытом виде. Если .tfstate попадёт в Git или иное доступное место, ключ скомпрометирован, а вместе с ним — все серверы, куда этот ключ установлен. Меры: удалённый бэкенд с шифрованием и контролем доступа, хранение секретов в HashiCorp Vault (или аналоге) с передачей в Terraform через ссылки, а также обязательный .gitignore для *.tfstate и файлов состояния в целом.
