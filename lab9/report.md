# Отчет по лабораторной работе №9
## Тема: Stateful-приложения, автомасштабирование (HPA) и отказоустойчивые базы данных (Patroni) в Kubernetes


###  Ответы на контрольные вопросы

1. Как работает Headless Service и зачем нужна сетевая идентичность подов?
Headless Service — сервис с clusterIP: None, который не даёт единого виртуального IP и не распределяет трафик между подами. Вместо этого для каждого пода StatefulSet создаётся отдельная DNS-запись A.
При запросе nslookup web-stateful-svc возвращается набор адресов всех подов, а nslookup web-stateful-0.web-stateful-svc — ровно один IP конкретного экземпляра pod-0.
Это необходимо приложениям с состоянием (например, СУБД): клиенту нужен стабильный адрес конкретного узла (скажем, текущего лидера), а не случайный под за балансировщиком.

2. Почему для HPA обязательны requests, и как считается утилизация?
Без resources.requests.cpu механизм HPA не может построить расчёт. Формула такая:
Текущая утилизация (%) = (суммарное потребление CPU всеми подами) / (сумма requests.cpu всех подов) × 100%.
Если requests не заданы, нет «точки отсчёта» для процентов: HPA не поймёт, достигнут ли порог averageUtilization, масштабирование не сработает, а в статусе будет <unknown>.

3. Что происходит с PVC при удалении StatefulSet и как сохранить данные?
После kubectl delete statefulset web-stateful PVC остаются — это защитный механизм Kubernetes по умолчанию, чтобы не потерять данные при удалении контроллера.
Если же выполнить kubectl delete pvc data-web-stateful-0, том удалится безвозвратно вместе с данными.
Чтобы удалить StatefulSet и сохранить данные, достаточно удалить только контроллер. PVC останутся в статусе Bound, и при повторном применении манифеста с теми же volumeClaimTemplates поды подхватят существующие тома.

4. Зачем Patroni нужен DCS и как он предотвращает Split-Brain?
В данной конфигурации DCS — это сам Kubernetes API (через объекты Endpoints): Patroni хранит там состояние кластера и сведения о лидере.
Защита от Split-Brain строится на механизме lease (аренды): лидер периодически обновляет свою запись о лидерстве в DCS. Если связь с API теряется, аренда истекает, и узел принудительно переводит БД в read-only или останавливает её. Master'ом может стать только тот, кто успешно захватил и удерживает lease в DCS. Так гарантируется, что активный Master в любой момент ровно один.

5. Как synchronous_commit: "on" влияет на запись, производительность и RPO?
При таком параметре главный узел не подтверждает клиенту COMMIT, пока не получит подтверждение, что WAL-записи сохранены на диске хотя бы одной синхронной реплики.
Производительность: латентность записи растёт, так как операция ждёт сетевого обмена с репликой.
Надёжность: RPO = 0 — при внезапном отказе лидера ни одна подтверждённая транзакция не теряется, ведь она уже есть на реплике, которая станет новым лидером.

6. Зачем HPA ждёт перед масштабированием вниз?
Период ожидания (по умолчанию 5 минут) перед scale down нужен для борьбы с «flapping» (дребезгом). При мгновенном снижении реплик на кратковременном спаде нагрузки система постоянно создавала бы и удаляла поды: это лишние затраты CPU на запуск/остановку контейнеров и нестабильность приложения. Cooldown гарантирует, что снижение нагрузки — устойчивый тренд, а не короткий всплеск.
