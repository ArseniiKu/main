# Отчёт A: Terraform и Import

1. Почему tofu plan перед импортом показывал создание ресурсов, хотя они уже существовали?

Потому что plan — это сравнение двух источников: конфигурации и файла состояния. Реальная инфраструктура в этом сравнении напрямую не участвует. На момент проверки state был пуст, то есть Terraform располагал только описанием желаемого результата из main.tf и не имел ни одной записи о фактически существующих объектах. Для него ситуация выглядела так: «в коде ресурсы есть, в state — ничего», а значит, их нужно создать. Существующие контейнеры в LXD для Terraform как бы не существовали, пока они не были занесены в state через импорт.

2. Что конкретно tofu import записывает в terraform.tfstate?

Команда устанавливает соответствие между двумя вещами: адресом ресурса в конфигурации (например, lxd_instance.existing_nodes["node1"]) и уникальным идентификатором этого объекта во внешней системе (для LXD — имя контейнера, node1). Именно эта пара «адрес в коде ↔ идентификатор в реальном мире» и фиксируется в state. После этого Terraform при последующих запусках понимает, что за ресурсом в коде стоит конкретный существующий контейнер, и может отслеживать его состояние и управлять им. Никаких других данных об инфраструктуре импорт сам по себе не создаёт — он лишь «привязывает» объект к адресу.

3. Что произойдёт, если после импорта поменять limits.memory = "4GiB" и выполнить terraform apply?

Terraform обнаружит расхождение между желаемым (4 GiB) и текущим (то, что записано в state после импорта) значением и построит план изменения. Поскольку LXD позволяет менять лимит памяти у работающего контейнера без его пересоздания, изменение будет выполнено как обновление на месте (~ update in-place). Контейнер не будет ни удалён, ни остановлен — новый лимит применится к уже работающему экземпляру. Важно, что такое поведение определяется возможностями провайдера и самой платформы: если бы LXD не поддерживал горячее изменение, план мог бы предполагать пересоздание ресурса.

4. Почему terraform.tfstate нельзя коммитить в Git?

Причин две, и они независимы. Первая — безопасность: state хранит значения атрибутов ресурсов, среди которых могут быть пароли, токены, приватные ключи и адреса в открытом виде; попадание файла в репозиторий равносильно утечке этих данных. Вторая — согласованность при командной работе: state — это единственный «источник правды» о том, чем управляет Terraform, и если его версия расходится у разных участников (или перезаписывается при merge), возникают конфликты и рассинхронизация, чреватые ошибочными планами и потерей контроля над инфраструктурой. Поэтому state выносят в защищённый удалённый бэкенд (например, S3 с шифрованием и блокировками), а локальные файлы состояния исключают через .gitignore.
